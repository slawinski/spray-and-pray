# Spray and Pray (SAP)

> A terminal-native, single-user job application engine. It tracks applications, generates AI-tailored, ATS-optimized CVs **and cover letters**, runs mock interviews, and turns interview weaknesses into interactive learning content.

**Spray and Pray** automates the most tedious parts of a job search so a solo job-seeker can focus on preparing and interviewing — not copy-pasting job descriptions and reformatting PDFs.

## What it does

SAP is a personal pipeline for the entire application lifecycle:

1. **Capture** a job posting (1-click from a browser extension, or a local JD file).
2. **Optimize** your Master CV and generate a matching cover letter — both tuned to pass Applicant Tracking Systems (ATS) while reading like a human wrote them.
3. **Track** every application through a status state machine (draft → applied → ghosted → interview N → offer → accepted/rejected/withdrawn).
4. **Prepare** with role-specific mock interviews, evaluated by an LLM with a readiness score.
5. **Learn** from your weaknesses with auto-generated, interactive lessons.

Everything runs locally. There is no backend service, no account, and no data leaves your machine except the LLM API calls.

## Features

### 1. ATS-Optimized CV Generation
- Takes a `master_cv.json` and a job description, produces a tailored CV in Markdown.
- Uses the application's selected **IT**, **Mechanical Engineering**, or **Baker** profile to select eligible facts before writing; the full career record is not sent to the document writer.
- Uses a dedicated LLM prompt (`cv_optimizer/prompts/optimize.md`) that enforces:
  - **Exact keyword matching** — literal string comparison against the JD (e.g. `React.js` not `React`).
  - **Anti-hallucination** — every skill and achievement must trace back to the Master CV. Gaps are never fabricated.
  - **Front-loaded keywords** in the Summary and first Experience bullets.
  - **Human readability first** — ATS passes get you screened, but a recruiter gets you hired.
- Renders a styled two-column PDF (header, sidebar with skills/contact, main column with experience/education).
- Optionally embeds a candidate photo (`candidate.jpeg`) top-left in the header, sized to match the name + title block. Baker CVs always suppress this photo.

### 2. ATS-Optimized Cover Letters
- Generates a tailored cover letter alongside the CV (`cv_optimizer/prompts/cover_letter.md`).
- 250–400 words, narrative prose with JD keywords woven naturally (not keyword-stuffed).
- Enforces ATS signals: exact role-title match, company-name personalization, front-loaded keywords, strong action verbs, no passive voice.
- Renders a clean, single-column letter PDF (name/contact header, date, `Re:` line, salutation, body, sign-off).
- Cover letters are generated by default whenever an application is tracked through the browser extension.

### 3. 1-Click Browser Extension
- Chrome/Firefox extension (Manifest V3, vanilla JS) that scrapes the current tab's job posting and POSTs it to the local API.
- Supports job boards with site-specific selectors plus a JSON-LD fallback:
  - LinkedIn, justjoin.it, nofluffjobs.com, theprotocol.it, greenhouse.io, workingnomads.com
- After explicit profile selection, starts generation of the JD copy, CV (`.md` + `.pdf`), and cover letter (`.md` + `.pdf`) on a single click. Documents become ready only after successful checking and publication; completion can be partial.

### 4. Application Tracking
- SQLite database (WAL mode) persists every application with its status history.
- A status state machine with flow constraints prevents nonsense transitions (e.g. circular ghosted/applied toggling, "un-rejecting" an offer):
  - `draft` → `applied` → `ghosted` → `interview 1` → … → `interview N` → `offer` → `accepted` / `rejected` / `withdrawn`
  - Draft activation auto-inserts `ghosted` (pessimistic default).
  - Ghosted is replaced by any real outcome (interview/offer/accepted/rejected/withdrawn).
  - `withdrawn` is candidate-initiated: selectable from `applied`, `interview N`, or `offer` — never from `ghosted` silence.
  - Backtracking (undo) is supported cleanly.
- Edit a tracked application (`e` key: company, role, job URL) to fix bad auto-import scrapes — renames the application directory and role-derived JD/CV/cover-letter files and repoints the stored paths.
- Per-application filesystem directories (`applications/{company}_{role}_{id}/`) hold the JD, CV, and cover letter.

### 5. Terminal UI Dashboard
- Interactive Textual dashboard (`./cv-opt`) — no browser needed.
- Paginated, filterable table with a detail panel and a status bar.
- Full keyboard navigation (see [Usage](#usage)).

### 6. Sankey Funnel Visualization
- Aggregates application transitions into a funnel (`applied → interview 1 → … → offer → accepted`).
- Renders as an ASCII table in the terminal, or an interactive Plotly Sankey diagram in the browser.
- Ghosted entries are intelligently cleaned (transient ghosted periods are stripped; terminal ghosted kept).

### 7. Mock Interviews
- Generates role-specific questions (behavioral, technical, system design, coding) from the JD, Master CV, and optional `company_intel.json`.
- Browser-based interview session with a Monaco code editor, hint system, and progress bar.
- LLM evaluation produces per-question feedback, strengths/weaknesses, and a 0–100 readiness score.
- Weaknesses link to "Deep Dive" lessons (see below).

### 8. Learning Aide
- Generates blog-like interactive lessons from interview weaknesses (or any concept).
- Lessons embed live Monaco code editors, Chart.js charts, Mermaid diagrams, and interactive widgets.
- A persistent lesson library (`/learn`) and a D3.js knowledge graph (`/graph`) grow organically.

## Installation

### Prerequisites

- **Python 3.12+**
- A working **LLM API key** (DeepSeek by default, or any OpenAI-compatible endpoint)
- **macOS** (notifications and "Reveal in Finder" use `osascript` and `open`; other platforms will work but lose those conveniences)

### Steps

```bash
# 1. Clone and enter the repo
git clone <repo-url> spray-and-pray
cd spray-and-pray

# 2. Create a virtual environment
python3 -m venv .venv
source .venv/bin/activate

# 3. Install dependencies (no requirements.txt — install directly)
pip install fastapi uvicorn jinja2 markdown pymupdf openai \
            pydantic python-dotenv unidecode requests textual

# 4. Configure environment
cp .env.example .env
#    Edit .env and set DEEPSEEK_API_KEY (and optionally DISCORD_WEBHOOK_URL)

# 5. Create your Master CV
cp master_cv.example.json master_cv.json
#    Fill in your real data (see Data model below)

# 6. (Optional) Add company interview intel
#    Create company_intel.json (see Data model below)
```

> **Note:** There is no `requirements.txt` or `pyproject.toml` — dependencies are managed ad hoc. If you want reproducible installs, consider pinning them with `pip freeze > requirements.txt`.

Automated job discovery is configured through `job_search.json` (see the

| Setting | Default | Description |
|---|---|---|
| `enabled` | `true` | Master switch for discovery |

```bash
./cv-opt
# or: python3 cv_optimizer.py
```

| Key | Action |
|---|---|
| `q` | Quit |
| `r` | Refresh |
| `/` | Reveal and focus filter (Enter/Escape returns without clearing) |
| `?` | All actions, including Reports (server must be running), Clear filter, Terminal funnel, and Operation status |
| `enter` | Open complete, scrollable application details |
| `e` | Edit company, role, and job URL |
| `s` | Change status |
| `o` | Open application folder in Finder |
| `ctrl+r` | Re-generate CV |
| `ctrl+g` | Generate cover letter |
| `v` | Select or change the application's CV profile |
| `P` | Prepare mock interview (opens browser) |
| `L` | Open lesson library (browser) |
| `S` (Shift+S) | Generate and open the interactive Sankey diagram in the browser |
| Arrows / Home / End / Page Up / Page Down | Navigate continuously through filtered applications |
| `T` | Set source (e.g. "Referral") |
| `u` | Open job posting URL |
| `J` | Run automated job discovery (background worker) |
| `m` | Generate Match Score for the selected application |
| `M` | Backfill Match Scores for all applications missing one |
| `D` | Delete application |
| `escape` | Cancel dialog / close details / return from filter |

The dashboard supports panes **40 columns × 12 rows** and larger. Below 80
columns it shows compact records; at 80 columns it uses a fluid
table. At 180 columns × 18 rows and above, a right-hand inspector follows the
selected application. Short panes hide the header and show the filter only
while in use. Taller panes expose more records without pages. Resizing retains
selection, filters, open dialogs, unsaved edits, and background work. Below the
minimum a resize prompt blocks input without closing the current screen.
Dialogs keep confirmation controls separate from their scrollable content;
use Tab/Shift+Tab to reach fields and buttons, and arrows to scroll. Discovery
is shown only when enabled. The original interactive shortcut footer lists
the available key bindings; scroll it horizontally when they do not all fit.
`?` provides the full action list and operation feedback. Dialogs retain their
centered 50-column layout, thick borders, spacing, and centered buttons when
space permits, becoming compact and scrollable in small panes.

The table always keeps **Added** (date added), **CV**, and **CL** visible.
CV and CL use separate checkmarks for generated documents, a dash when absent,
and a rotating arrow while generation is running. Compact records show the
same document indicators and date on a labelled fourth line. Optional metadata
yields space before these fields or the company and role columns.

Application details and the inspector share formatted sections for overview,
match evidence, documents, job information, discovery, and status history.
Bold labels and colored headings separate fields; evidence and history use
individual list entries, and document availability is separated from file paths.

The application table shows a **Match** column (from `match-v2`): `85–100`
bold green, `70–84` yellow, `55–69` orange, `<55` dim red. Auto-discovered
applications show their `auto:<provider>` source. The inspector and full details split
evidence into **Strong** (direct), **Transferable** (framework transfer —
e.g. "Svelte → React, Vue.js") and **Gaps**, plus discovery metadata
(posted/discovered dates, location, salary).

### 1b. Automated job discovery

```bash
./cv-opt discover              # fetch → dedupe → filter → score → import >=85
./cv-opt discover --preview    # no LLM calls, no imports (debug search config)
./cv-opt discover --no-import  # score + persist, no Draft creation
./cv-opt discover --source serpapi --max-scores 10
./cv-opt discover --rescore    # ignore the score cache
```

### 1c. Match-score backfill

Applications tracked before the Match Score feature (or whose scoring
failed) show `—` in the Match column. Backfill them from the TUI (`M` for
all missing, `m` for the selected row) or from the CLI:

```bash
./cv-opt score              # score every application missing a Match Score
./cv-opt score --force      # re-score every application that has a JD
./cv-opt score 3 12         # score specific application ids
./cv-opt score --json       # machine-readable summary
```

Applications without a stored JD are skipped and reported, one failing
application never stops the batch, and existing cached assessments are
reused (no duplicate LLM calls) unless `--force` is given.

Discovery runs without FastAPI or the TUI — it talks to SQLite, the match
engine, and the source adapters directly. Runs are serialized with a
`.discovery.lock` file; a concurrent run prints `Discovery already in
progress.` and exits.

**Pipeline order (cost-optimized):** fetch → normalize → dedupe (source ID →
canonical URL → company/title/location + JD similarity) → cheap prefilter
(interns/juniors/backend-only/foreign-geography/short JDs) → prioritized
score queue (newest, highest-confidence first, capped at
`max_scores_per_run`) → `match-v2` → qualification → transactional Draft
import. Dedupe and filtering happen **before** any LLM call; unchanged
JD/candidate/scoring identities reuse cached assessments.

**Why Drafts, not `applied`?** A discovered job is not an application until
the user decides to pursue it. Qualifying jobs (`>= 85`, active, not
dismissed) become `draft` applications containing the JD and the copied
Match Assessment — but never a generated CV or cover letter, and never a
fake `applied` status. Document generation stays a deliberate, per-job user
action in the TUI (`ctrl+r`, `ctrl+g`).

New discovery drafts have **no profile selected**. The first CV or cover-letter
action prompts for IT, Mechanical Engineering, or Baker; cancelling leaves the draft
unselected. The detail panel shows the stored choice. Use `v` to select or change
it explicitly. Each application's CV and letter reuse that choice independently
of other applications. Changing it clears both document-ready paths but leaves
the old files on disk; it does not generate replacements. Choosing the same
profile leaves readiness unchanged.

**Sources**

| Source | Mechanism | Notes |
|---|---|---|
| `serpapi` | Google Jobs via SerpApi (`SERPAPI_API_KEY`) | Broad market source; role-centric queries, bounded pagination, 429-aware |
| `lever` | `api.lever.co/v0/postings/{site}?mode=json` | Configure `sources.lever.sites` |
| `ashby` | `api.ashbyhq.com/posting-api/job-board/{board}` | Compensation included; configure `sources.ashby.boards` |
| `greenhouse` | `boards-api.greenhouse.io/v1/boards/{board}/jobs` | Public boards; configure `sources.greenhouse.boards` |

One failing source never stops a run; rate-limited sources stop for that
run only.

**Dismissal & lifecycle.** Deleting an auto-imported Draft marks its
discovery record `dismissed`, so the next run does not re-import it.
Direct ATS postings missing from two consecutive polls become `inactive`
and are never auto-imported. Jobs below the threshold stay in
`job_postings` with their score, ready for reconsideration.

**Notifications.** One batched macOS + Discord summary fires only when new
Drafts were actually imported — never a "0 new jobs" message. Discord
failures never fail discovery.

**Scheduling (macOS).**

```bash
scripts/install_discovery_launchd.sh    # daily at 08:00 (no hardcoded paths)
scripts/uninstall_discovery_launchd.sh
```

The launch agent runs `<repo>/.venv/bin/python <repo>/cv_optimizer.py discover`.

### 1d. Search Focus Reporting

Start the existing local server, then open **http://localhost:8000/reports**,
or choose **Reports (server must be running)** from the dashboard's `?` action
palette. The action opens the URL only; it does not start a server or need a
selected application. Existing Shift+S browser Sankey and Terminal funnel
actions are unchanged.

```bash
uvicorn server:app --host localhost --port 8000
```

The overview leads with up to three evidence-backed investigation leads and a
Sankey summary. Navigation opens channel, cohorts, stage loss, targeting, skill
gaps, aging, opportunity inventory, and full Sankey views. Each report has a
readable table alongside its native chart. Use ordinary links/buttons with
Tab and Enter to inspect exact supporting records; evidence headings receive
focus. Reporting assets are local HTML/CSS/JavaScript/SVG with no CDN or remote
chart dependencies (the older standalone Plotly Sankey is separate).

**Scope and refresh.** Application reports initially include all recorded
application dates, profiles and sources. Applied-date bounds are inclusive UTC
calendar dates based on the first valid applied event, not creation time;
outcomes after the end date remain part of those applications' histories.
Profile/source filters and dates persist in the URL across report navigation.
Inventory always uses a separate **all captured postings** scope, retaining
the application filters for return navigation. A retrieval time identifies the
accepted snapshot. Refresh reads fresh local records and atomically replaces
the bundle, including its evidence. Failed loads mark retained data stale;
retry or navigate elsewhere. Empty selections, missing optional data and failed
loads have different states. Reporting never initializes or repairs a missing
or incompatible database.

**Definitions and limitations:**

- Outcome denominators count distinct records with a recorded applied event;
  never-applied drafts are separate. Unknown applied dates remain in all-dates
  scope but are excluded from explicit date ranges. Current status and ever
  reaching a stage are different measures; equal status timestamps use history
  ID order. Sankey counts transition occurrences, not applications summed over
  edges, and excludes draft-only preparation and transient ghosted steps.
- Automatic `ghosted` means **no recorded outcome**, not confirmed employer
  ghosting. Aging separates waiting before and after engagement. All durations
  are **recorded time**: activation, backfilling, undo and deleted history limit
  historical accuracy. Timezone-free timestamps are interpreted as UTC.
- Cohorts start on Monday in UTC. A 7/14/30-day interview window is unavailable,
  not zero, until every cohort member has that much recorded follow-up.
- Labels normalize Unicode, whitespace and case; exact source and role aliases
  merge conservatively and retain raw variants. Missing sources stay unknown,
  never inferred as cold applications. Recruiter groups have selection bias;
  descriptive incidence is not a causal channel comparison.
- Targeting separates latest descriptive fit from strictly pre-outcome
  assessments. Retrospective, tied/unknown timing, missing and invalid inputs
  remain separate. Comparisons partition scoring/prompt version, model and
  candidate hash. Reporting score bands (0–39/40–59/60–79/80–100) are fit bands,
  not interview probabilities or the matching tool's named labels.
- Skills audit recorded CV evidence, not demonstrated inability or employer
  rejection reasons. Partial, none and unknown stay distinct. Counts are
  distinct applications within each cell; overlapping evidence columns need
  not sum to the row total.
- Comparison leads require two known groups of at least 10 applications each,
  five interviews combined, fully observed 30-day follow-up and a difference
  of at least 10 percentage points in 30-day attainment. Targeting also needs
  comparable pre-outcome provenance. Descriptive channel concentration needs
  at least 3 of 5 recorded interviews. Skill leads need 10 valid assessed
  applications and 5 with partial/none must-have/core evidence (union counted
  once). These editorial thresholds are not statistical significance or
  recommended effort allocations. Otherwise the brief says insufficient data.
- Inventory describes captured postings, not the current market. Freshness and
  recorded collection errors remain visible; records older than 30 days are
  not inferred inactive. Salary currencies, pay periods and employment types
  stay separate; missing units are non-comparable. Absent application links
  cannot establish source-to-application yield.

**Read-only boundary.** Reporting reads one SQLite transaction (including
committed WAL data) and closes it before aggregation. Opening, filtering,
inspecting and refreshing reports do not edit applications, history,
assessments or discovery records, generate assessments, run discovery, or open
local files. SQLite may maintain WAL shared-memory bookkeeping; logical data
and schema are protected, not byte-identical SHM files. Keep the server on
loopback: reporting rejects explicit foreign browser origins and removes CORS
allow headers, but has no authentication and permits origin-free local clients.

### 2. Browser extension

1. Start the server: `uvicorn server:app --host localhost --port 8000`
2. Load the `extension/` directory as an unpacked extension:
   - Chrome: `chrome://extensions` → Developer mode → *Load unpacked*
   - Firefox: `about:debugging` → *Load Temporary Add-on*

4. The completion notification distinguishes tracked-only failure, CV ready with letter failure, and both documents ready. An accepted request alone does not mean documents are ready.

| `GET` | `/prepare-interview/{app_id}` | Loading screen → interview |
| `GET` | `/interview/{session_id}` | Interactive interview page |
| `POST` | `/api/interview/{session_id}/answer` | Save an answer |

| `GET` | `/api/interview/{app_id}/latest` | Latest readiness score |

| `GET` | `/learn` | Lesson library |
| `GET` | `/graph` | D3.js knowledge graph |
| `GET` | `/prepare-learn?concept=...` | Loading screen → lesson |

`/api/track` rejects missing, null, empty, or unknown `cv_profile` values before
scheduling generation or inserting an application. Older clients must send this
field; omission is not an IT default. Direct new `track()` calls also require an
explicit valid choice. Existing applications receive IT on the one-time profile
migration, without rewriting saved files or retroactively checking them. Newly
inserted drafts remain unselected across restarts. ID-only generation on an
unselected application fails: select its profile in the TUI first.

Before publication, each generated CV and letter is checked independently against
the selected facts and exclusions. This adds **one checker completion per
document**, using the configured provider/model, in addition to writing costs.
Content checking is **advisory**: excluded employment titles/identities, semantic
findings, malformed verdicts, and checker/provider failures warn and still publish.
Literal skill bans are removed entirely. Full reasons and excerpts stay in local
logs; TUI and server completion notifications show safe warning summaries. An
incomplete check is never reported as passed, and warning delivery cannot block
publication. No automatic correction or checker retry loop runs.

Profile selection and valid source projection remain required. Writer, renderer,
and transactional publication failures still fail the attempt. A failed
same-profile replacement preserves the prior files and ready path; after a profile
change, old files remain on disk but are not marked ready. In-flight output for an
outdated selection cannot publish.

## Data model

### Master CV (`master_cv.json`)

The shared factual career record lives at `master_cv.json` by default (the
`master_cv_path` setting in `cv_optimizer/config.py`; a per-call source override
must satisfy the same policy). Keep personal data local and ignored. Start from
[`master_cv.example.json`](master_cv.example.json), the complete synthetic format
example, and replace its fictional facts and profile selections with your own.

The existing `personal_info`, `summary`, `skills`, `experience`, education, and
other factual sections remain canonical. Profile metadata controls document
eligibility rather than maintaining separate biographies:

- Give every experience and education record a unique, stable `id`.
- `profile_shared` explicitly lists personal-info **field names**, exact language
  entry snapshots, and the exact source `disclaimer` string (or `null` to omit
  consent text). It does not copy unknown fields automatically.
- Each prepared policy (`profiles.it`, `profiles.mechanical_engineering`, `profiles.baker`) requires an approved
  `headline`, a `summary` string or structured-object snapshot, `roles`, `skills`,
  and `education`. Positioning is approved per profile, not taken implicitly from
  the unrestricted master summary or most recent job title. Historical job titles
  and dates remain factual; an engineering headline does not assert current
  mechanical practice.
- `roles` maps stable IDs to `{"detail": "detailed" | "brief",
  "achievements": [...]}`. Each achievement selector must exactly match a source
  string in that role. `skills` maps source category names to exact source values;
  `education` lists stable IDs for complete education views. Source order is
  retained, so keep experience in truthful reverse chronology.
- Mechanical profiles may add `"cv_role_detail": {"software": "ledger"}` using
  their selected role IDs. Each ledger role keeps its historical title, company,
  supplied location and dates as a compact, wrapping identity row in Experience,
  with **zero achievements or descriptive prose**. This override applies only to
  CV generation; the original `roles` selections still govern cover letters.
  Add every IT role intended for the ledger explicitly—ordinary `brief` roles
  keep their existing presentation. Overrides on the IT profile are not allowed.
- Optional `speaking_and_community` and `certifications` selectors are exact
  source-entry snapshots; `hobbies` selectors are exact strings. Omission selects
  nothing. Newly added facts are not automatically eligible for any profile.

### Preparing Baker documents

Keep your real data in ignored `master_cv.json`; the shipped example and automated
tests are synthetic, not the candidate's baking or career record. Existing masters
with only IT and engineering policies remain valid; requesting an unprepared Baker
policy fails rather than falling back to another narrative.

Add canonical `home_practice`, `workshops`, and `portfolio_links` arrays and select
their exact record snapshots under `profiles.baker`. Only Baker accepts these
selectors; omission selects nothing. Practice records allow `title`, `context`,
`start_period`, `bake_count`, `batch_size`, `sharing_context`, and `activities`
(a list of strings). `frequency` is optional for records that actually need it;
do not invent a regular schedule. Bake counts mean sessions, not loaves, and
"up to" batch sizes are upper bounds. Bread shared with friends on private trips
is hobby practice, not catering or commercial production.
Workshop records allow `name`, `provider`, `attendance_period`, `instructor`, and
optional `url`. Portfolio records allow `label`, `url` and an optional `description`,
so a self-built baking app can be linked and described alongside a baking portfolio.
Use the live app URL rather than its source repository. Preserve approximate
dates and quantities as strings rather than inventing exact dates. Add only
confirmed techniques to a baking skill category and select its exact strings in
Baker, not the other document profiles. Do not infer skills from images or syllabi.

For a short career overview, set `profiles.baker.career_summary` to an approved
paragraph and `roles` to `{}`. Individual employers, titles and dates are then
excluded from the writer; the career summary replaces the role-by-role history.
Older Baker policies without `career_summary` can still select `brief` roles.
Select the existing concise degree view. Baker projects only degree and university
(plus the internal ID); it omits dates, thesis and specialization. Do not copy
example career IDs into a real master or change existing IT/engineering policies.

Baker CVs foreground **Home Baking Practice**, then **Workshops**, **Other
Employment** and **Education**, after Summary. The sidebar includes a labeled,
clickable **Portfolio** links and selected descriptions alongside contact, skills
and languages. Baker omits LinkedIn and GitHub from the selected contact fields.
Polish JDs
use Polish documents, including **Domowa praktyka piekarska**, **Warsztaty** and
**Pozostałe zatrudnienie**. No photographs are embedded. The same selected facts
govern initial and regenerated letters. Hobby practice is not paid employment,
and workshop attendance is not certification or professional experience. Advisory
checks flag inflation, unsupported commercial/credential claims, missing selected
sections/portfolio and excluded technical achievements; they do not block publication.

Source and selector edits take effect on the next generation or regeneration;
they never rewrite saved files or change an application's selection. Review the
generated Markdown and PDF in both languages before applying. Baker adds document
eligibility, not bakery discovery, profile-aware scoring or interview behavior.

For example, retain the original concise IT master's record as `msc-it`; add
separate expanded master's and bachelor's records (`msc-expanded`, `bsc`) for
engineering. IT selects only `msc-it`, preserving its original values and concise
presentation (attendance dates omitted as before). Engineering selects the two
expanded records, including supplied dates, specializations, and theses. IT
excludes historical mechanical employment entirely, not just its bullets, and
mechanical-only skills. Engineering selects detailed historical engineering work
and recent IT roles as identity-only CV ledger rows. The example retains the
original brief IT achievement selections for mechanical cover letters; no career
facts are deleted. Both role types remain in global reverse chronology, including
when IT and engineering employments alternate. Ledger rows use Markdown
blockquote paragraphs (`> **Title** | Company | Location | Dates`), separated by
blank quoted lines, inside the single Experience section. PDF rendering gives
them compact spacing at normal body text size, with natural wrapping.

Adding the override does not rewrite saved Markdown or PDFs. New generation or
explicit regeneration uses it. Existing policies without `cv_role_detail` retain
their original behavior. Content checks remain advisory; this introduces no page
limit, content-blocking check or automatic rewrite loop.

When editing selected source text, update its exact selector too, including
language, community, and certification snapshots. Duplicate IDs, ambiguous or
dangling references, wildcards, missing prepared policies, and invalid supplied
policies stop generation with a configuration error. There is no raw-master
fallback; all supplied policies are validated even when only one is requested.

The old-CV recovery was a **one-time candidate-reviewed import**, not a reusable
import tool. Only confirmed source facts belong in the master; absent metrics,
tools, issuers, dates, and current proficiency must remain unclaimed. Keep old
personal documents and extraction drafts out of tracked fixtures.

Matching and discovery still consume canonical master facts independently of
document profiles. Enriching career facts can change match scores/cache identity;
this feature does not add profile-aware scoring or interview generation.

### Match Score v2 — framework transferability

The Match Score (docs/specs/MATCHING_SCORE_SPEC.md) gained a `match-v2`
scoring version with a new evidence taxonomy:

| Level | Value | Meaning |
|---|---|---|
| `direct` | 1.00 | Exact skill evidenced in the Master CV |
| `framework_transfer` | 0.92 | Named mainstream JS framework absent, but other mainstream JS framework production experience exists and the JD does not demand framework-specific depth |
| `strong_transfer` | 0.75 | Closely transferable non-framework evidence |
| `framework_depth_gap` | 0.60 | Exact framework depth is central to the role (e.g. "6+ years Angular") |
| `partial` | 0.40 | Some relevant evidence |
| `unknown` | 0.50 | Non-skill facts the CV cannot establish |
| `none` | 0.00 | No evidence — hard-gap caps still apply |

The framework family (React, Next.js, Preact, Vue, Nuxt, Angular, Svelte,
SvelteKit, Solid, SolidStart, Ember, Qwik, Lit + aliases) is validated in
Python: the LLM proposes a level, but only genuine JS-frontend-framework
names may receive `framework_transfer`/`framework_depth_gap`, and the
profile must evidence at least one *other* framework. React does not
"transfer" to Django or Kubernetes. Framework transfer never triggers the
missing-core hard caps (`<=69` / `<=54`); a genuinely absent independent
must-have still does. Historical `match-v1` rows remain stored and versioned.

## Testing

Install `pytest` and a compatible `httpx` for FastAPI TestClient tests. Node.js
must be on PATH for reporting browser-state, rendering and integration checks;
their Node-backed checks must actually run before shipping (not silently skip).
No npm dependencies or paid model calls are needed for reporting tests.

```bash
pip install pytest httpx
python3 -m pytest tests/test_reporting*.py tests/test_sankey.py -q
```

Reporting tests use temporary synthetic SQLite databases, with initialization
and writer failure sentinels installed after fixture setup. Never run mutation
or concurrency experiments against your personal `applications.db`. HTTP and
Node DOM-harness checks cover bundle consistency and evidence navigation;
real-browser desktop/390px keyboard, contrast, offline-assets and refresh/retry
QA remains a separate check against an isolated fixture-backed server.

```bash
python3 -m pytest tests/ -q
```

Key suites:

- `tests/test_framework_transferability.py` — `match-v2` evidence taxonomy, framework-family validation, hard-cap interactions (no LLM calls)
- `tests/test_discovery_filters.py` — deterministic prefilter (geography/role/seniority/JD length)
- `tests/test_discovery_dedupe*.py` — URL normalization, fingerprints, cross-source merge, false-split protection
- `tests/test_discovery_sources.py` — fixture JSON → `DiscoveredJob` normalization for all four providers
- `tests/test_discovery_importer.py` — transactional Draft import, threshold, dismissal lifecycle
- `tests/test_discovery_integration.py` — end-to-end runs with a fake source and mocked LLM (cache, budget, isolation, modes)
- `tests/test_source_persistence.py` — `source` persistence + migration-from-existing-DB regressions

All provider network calls are mocked or fixture-backed; live integration
tests are intentionally opt-in.

## Constraints & limitations

- **Single-user, local-only.** No authentication, multi-tenancy, or remote hosting. The API binds to `localhost` and assumes one operator.
- **macOS-centric.** Notifications (`osascript`) and "Reveal in Finder" (`open -R`) are macOS-only. Other platforms work but lose those conveniences.
- **LLM dependency.** CV, cover letter, interview, and lesson generation all require a reachable LLM API and consume tokens (cost/time). Generation is synchronous in the TUI (`ctrl+r`, `ctrl+g`) and backgrounded in the server.
- **No dependency lockfile.** Dependencies are installed ad hoc; there is no `requirements.txt` or `pyproject.toml`. Pin them for reproducibility.
- **Personal data is gitignored.** `master_cv.json`, `applications.db`, and `applications/` are not version-controlled. Back them up yourself.
- **PDF layout is fragile.** The CV PDF uses hard-coded dimensions (A4 mediabox, fixed sidebar width). Large deviations in content length or diacritics may need layout tuning.
- **Checks are not a correctness guarantee.** Source projection limits writer input; deterministic and independent semantic checks warn about detected violations before publication. Checks are advisory and can still miss errors. Always review generated CVs and letters before submitting.
- **ATS optimization is heuristic.** "ATS-optimized" means following well-known parser heuristics (literal keyword matching, clean text, standard headings) — it does not guarantee passage through any specific ATS vendor.
- **Cover letter scope.** The cover letter generator assumes a generic "Dear Hiring Manager" salutation; it cannot infer a specific recruiter's name.

## Security & privacy

- **Your personal data** (name, phone, email, work history) is sent to the LLM provider in every generation request. Choose a provider you trust; this is the only place data leaves your machine.
- **Existing extension endpoints have open CORS** (`allow_origins=["*"]`). Any website can POST to those local endpoints while the server is running; a malicious page could trigger generations. Reporting paths (`/reports`, `/api/reports/snapshot`) reject explicit foreign browser origins and strip CORS allow headers. This is not authentication. The server never exposes raw Master CV contents over HTTP.
- **No authentication** on the API. Do not expose port 8000 to the network.
- **Discord webhook** (if configured) receives success/failure summaries, including company/role names.
